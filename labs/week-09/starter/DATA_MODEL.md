# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

---

## 1. ภาพรวม

```text
users                              requests
-----------------                  -----------------
id (PK)                            id (PK)
name                               requester_id (FK)
department                         request_type
email                              location
                                   details
                                   priority
                                   status
                                   created_at

users.id  1  ----------------  หลาย  requests.requester_id
```

จากที่ออกแบบ ตาราง `users` กับ `requests` เป็นความสัมพันธ์แบบ **หนึ่งต่อหลาย (One-to-Many)** เพราะ user 1 คนสามารถมีคำร้องได้หลายคำร้อง โดยใช้ `requester_id` ในตาราง `requests` เชื่อมกับ `id` ของตาราง `users`

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ตอน Week 06–07 เราเก็บ `requesterName` เป็นข้อความไว้ในคำร้องแต่ละรายการ วิธีนี้ใช้งานได้ตอนที่ข้อมูลยังไม่เยอะ แต่ถ้าผู้ใช้คนเดิมส่งคำร้องหลายครั้ง ชื่อของเขาก็จะถูกเก็บซ้ำอยู่หลายรายการ

ตัวอย่างเช่น ถ้าสมชายมีคำร้อง 20 รายการ แล้วสมชายเปลี่ยนชื่อ เราจะต้องตามแก้ชื่อในคำร้องทั้ง 20 รายการ ถ้าแก้ไม่ครบก็อาจทำให้บางรายการเป็นชื่อเก่าและบางรายการเป็นชื่อใหม่ ทำให้ข้อมูลไม่ตรงกัน

พอแยกข้อมูลออกเป็นตาราง `users` และ `requests` ข้อมูลของสมชายจะถูกเก็บไว้เพียงครั้งเดียวในตาราง `users` ส่วนใน `requests` จะเก็บแค่ `requester_id` เพื่อบอกว่าคำร้องนั้นเป็นของใคร

ดังนั้นถ้าสมชายเปลี่ยนชื่อ เราแก้แค่ 1 จุดในตาราง `users` คำร้องเดิมทั้งหมดก็ยังเชื่อมไปหาผู้ใช้คนเดิมได้เหมือนเดิม วิธีนี้ช่วยลดข้อมูลซ้ำและลดโอกาสที่ข้อมูลจะไม่ตรงกัน

## 3. รายละเอียดตาราง

### ตาราง `users`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT | ใช้เป็นรหัสผู้ใช้ภายในระบบ และให้ฐานข้อมูลสร้างหมายเลขต่อไปให้อัตโนมัติ |
| `name` | TEXT | NOT NULL | ผู้ใช้ทุกคนต้องมีชื่อ จึงไม่ควรปล่อยว่าง |
| `department` | TEXT | NOT NULL | ใช้บอกสาขาหรือหน่วยงานของผู้ใช้ และจำเป็นต่อการนำข้อมูลไปใช้งาน |
| `email` | TEXT | NOT NULL, UNIQUE | ผู้ใช้ต้องมีอีเมล และไม่ควรมีผู้ใช้สองคนที่ใช้อีเมลเดียวกัน |

### ตาราง `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผล |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | ใช้รหัสรูปแบบ `REQ-001` ทำให้อ่านและเข้าใจได้ง่ายกว่าตัวเลขอย่างเดียว |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY | ใช้เชื่อมคำร้องกับผู้ใช้ในตาราง `users` |
| `request_type` | TEXT | NOT NULL, CHECK | จำกัดประเภทคำร้องให้อยู่ในค่าที่ระบบรองรับ |
| `location` | TEXT | NOT NULL | คำร้องต้องระบุสถานที่เพื่อให้รู้ว่าปัญหาเกิดที่ไหน |
| `details` | TEXT | NOT NULL | ใช้เก็บรายละเอียดของปัญหาหรือสิ่งที่ผู้ใช้ต้องการ |
| `priority` | TEXT | NOT NULL, DEFAULT `normal`, CHECK | ถ้าไม่ได้ระบุความเร่งด่วนให้ใช้ `normal` และป้องกันค่าที่ระบบไม่รองรับ |
| `status` | TEXT | NOT NULL, DEFAULT `pending`, CHECK | คำร้องใหม่เริ่มต้นเป็น `pending` และจำกัดสถานะให้อยู่ในค่าที่กำหนด |
| `created_at` | TEXT | NOT NULL, DEFAULT เวลาปัจจุบัน | บันทึกเวลาที่สร้างคำร้องโดยอัตโนมัติ |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

### ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน

`users.id` ใช้ `INTEGER` และ `AUTOINCREMENT` เพราะเป็นรหัสภายในฐานข้อมูล เราไม่ได้จำเป็นต้องให้ผู้ใช้อ่านหรือจำรหัสนี้ จึงให้ SQLite สร้างหมายเลขต่อไปให้อัตโนมัติ เช่น `1`, `2`, `3`, `4`

ส่วน `requests.id` ใช้ `TEXT` เพราะรูปแบบรหัสคำร้องของระบบเป็น `REQ-001`, `REQ-002` เป็นต้น รหัสแบบนี้ช่วยให้ดูแล้วรู้ทันทีว่าเป็นรหัสคำร้อง และสามารถนำไปแสดงให้ผู้ใช้เห็นได้ง่ายกว่าตัวเลขอย่างเดียว

### ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว

ถึงแม้ API จะตรวจข้อมูลก่อนบันทึก แต่ฐานข้อมูลก็ควรตรวจข้อมูลอีกชั้นหนึ่ง เพราะข้อมูลอาจไม่ได้เข้ามาทาง API อย่างเดียว เช่น อาจมีการใช้ SQL เพิ่มหรือแก้ข้อมูลโดยตรง

ถ้ามีแค่การตรวจที่ API อย่างเดียว แล้วมีข้อมูลถูกเพิ่มจากช่องทางอื่น ก็อาจมีค่าที่ระบบไม่รองรับหลุดเข้าไปในฐานข้อมูลได้

ตัวอย่างเช่น `status` ของระบบกำหนดไว้เพียง

```text
pending
in-progress
completed
```

ถ้ามีคนพยายามบันทึกค่าอย่าง `cancelled` หรือค่าอื่นที่ไม่ได้กำหนดไว้ `CHECK` constraint จะไม่ยอมให้ข้อมูลนั้นถูกบันทึกลงฐานข้อมูล

ดังนั้นการตรวจที่ API ช่วยตรวจข้อมูลก่อนส่งเข้าฐานข้อมูล ส่วน `CHECK` constraint เป็นการป้องกันข้อมูลผิดที่ระดับฐานข้อมูลอีกชั้นหนึ่ง

## 5. ตัวอย่างการใช้ JOIN

ตัวอย่างการนำข้อมูลคำร้องมาแสดงพร้อมชื่อผู้แจ้ง

```sql
SELECT
  r.id,
  u.name AS requesterName,
  r.request_type,
  r.status
FROM requests AS r
JOIN users AS u
  ON r.requester_id = u.id
ORDER BY r.id;
```

ตัวอย่างผลลัพธ์ที่ได้

| id | requesterName | request_type | status |
|---|---|---|---|
| REQ-001 | สมชาย ใจดี | แจ้งซ่อม | pending |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | ขอใช้อุปกรณ์ | completed |
| REQ-004 | สมชาย ใจดี | แจ้งซ่อม | pending |
| REQ-005 | ปรียา ขยันยิ่ง | อื่น ๆ | pending |
| REQ-006 | สุภาวดี รักเรียน | แจ้งซ่อม | pending |
| REQ-007 | ธนกฤต ตั้งใจ | อื่น ๆ | in-progress |
| REQ-008 | ปรียา ขยันยิ่ง | ขอใช้อุปกรณ์ | completed |

คำสั่ง `JOIN` ทำให้เราสามารถเก็บเพียง `requester_id` ในตาราง `requests` แต่ตอนนำข้อมูลมาใช้งานก็ยังสามารถดึงชื่อจริงของผู้แจ้งจากตาราง `users` ได้

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

ตอน Week 07 ข้อมูลที่ API ส่งให้ React มีข้อมูลอย่าง `requesterName` อยู่ในแต่ละคำร้อง ทำให้ฝั่ง React สามารถนำชื่อไปแสดงได้ทันที

แต่หลังจากแยกฐานข้อมูลใน Week 09 ตาราง `requests` ไม่ได้เก็บ `requesterName` โดยตรงแล้ว แต่เก็บ `requester_id` แทน

เมื่อใช้ `JOIN` ระหว่าง `requests` กับ `users` เราสามารถดึงชื่อผู้แจ้งกลับมาได้อีกครั้ง ผลลัพธ์จึงมีลักษณะใกล้กับข้อมูลที่ API เคยส่งให้ React ใน Week 07

สิ่งที่สังเกตได้คือ ฐานข้อมูลไม่จำเป็นต้องเก็บข้อมูลทุกอย่างซ้ำในตารางเดียว เราสามารถแยกข้อมูลออกเป็นหลายตารางให้เหมาะสม แล้วใช้ `JOIN` ตอนที่ต้องการนำข้อมูลมารวมกันเพื่อส่งให้ API หรือแสดงบนหน้าเว็บได้
