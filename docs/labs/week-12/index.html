# Campus Service — ระบบ Full-Stack (ENGSE203 Week 11)

ระบบรับคำร้องขอใช้บริการภายในมหาวิทยาลัย · **React + Express API + SQLite** ทำงานครบวงจร

## สถาปัตยกรรม 3 ชั้น

```
┌─────────────┐   HTTP    ┌──────────────┐   SQL    ┌───────────┐
│  React      │ ────────► │  Express API │ ───────► │  SQLite   │
│  (frontend) │ ◄──────── │  (api)       │ ◄─────── │  campus.db│
└─────────────┘   JSON    └──────────────┘   rows   └───────────┘
   พอร์ต 5173              พอร์ต 3001              ไฟล์ในเครื่อง
```

| ชั้น | หน้าที่ | โฟลเดอร์ |
|---|---|---|
| Frontend | หน้าจอผู้ใช้ · เรียก API | `frontend/` |
| API | route · controller · service | `api/src/` |
| Database | เก็บข้อมูลถาวร | `api/data/campus.db` |

## วิธีรัน (development)

```bash

cd api
npm install
cp .env.example .env
npm run db:setup      # สร้าง campus.db จาก schema.sql
npm run dev           # API ที่ http://localhost:3001

# ชั้น frontend (อีก terminal)
cd frontend
npm install
npm run dev           # React ที่ http://localhost:5173
```

## วิธีรัน (production)

```bash
# build แบบเดียวกับ cloud (script อยู่ใน package.json ระดับบนสุด)
NODE_ENV=production npm install
NODE_ENV=production npm run build

# start — เสิร์ฟทั้งหน้าเว็บและ API จากพอร์ตเดียว
NODE_ENV=production PORT=10000 npm start
# เปิด http://localhost:10000
```

# API Contract — Campus Service Request API

**เวอร์ชัน:** 2.0.0 · **Base URL:** `http://localhost:3001`
**รูปแบบข้อมูล:** JSON (`Content-Type: application/json`)

> **API Contract คืออะไร** — ข้อตกลงระหว่างคนทำ front-end กับคนทำ back-end
> ว่าจะคุยกันด้วย endpoint อะไร ส่งอะไรไป ได้อะไรกลับ
> มีไว้เพื่อให้สองฝั่ง**ทำงานคู่ขนานกันได้** โดยไม่ต้องรอกัน

---

## โครงสร้างข้อมูล Request

| field | ชนิด | คำอธิบาย | ตัวอย่าง |
|---|---|---|---|
| `id` | string | รหัสคำร้อง · ขึ้นต้นด้วย `REQ-` · เซิร์ฟเวอร์สร้างให้ | `"REQ-001"` |
| `requesterName` | string | ชื่อผู้แจ้ง · อย่างน้อย 2 ตัวอักษร | `"สมชาย ใจดี"` |
| `requestType` | string | ประเภท · 1 ใน 4 ค่าที่กำหนด | `"แจ้งซ่อม"` |
| `location` | string | สถานที่ · ห้ามว่าง | `"ห้องปฏิบัติการ 301"` |
| `details` | string | รายละเอียด · อย่างน้อย 10 ตัวอักษร | `"เครื่องปรับอากาศไม่ทำงาน"` |
| `priority` | string | `"normal"` หรือ `"urgent"` | `"urgent"` |
| `status` | string | `"pending"` · `"in-progress"` · `"completed"` | `"pending"` |

**ค่าที่ยอมรับของ `requestType`** — `แจ้งซ่อม` · `บริการบัญชีผู้ใช้` · `ขอใช้อุปกรณ์` · `อื่น ๆ`

## Endpoints

| Method | Endpoint | คำอธิบาย | Request body | สำเร็จ | ผิดพลาด |
|---|---|---|---|---|---|
| `GET` | `/api/requests` | ดูคำร้องทั้งหมด | — | `200` + array | — |
| `GET` | `/api/requests?status=` | กรองตามสถานะ | — | `200` + array | — |
| `GET` | `/api/requests/:id` | ดูคำร้องใบเดียว | — | `200` + object | `404` ไม่พบ |
| `POST` | `/api/requests` | สร้างคำร้องใหม่ | Request (ไม่ต้องมี `id`, `status`) | `201` + object ที่สร้าง | `400` ข้อมูลไม่ถูกต้อง |
| `PUT` | `/api/requests/:id` | เปลี่ยนสถานะ | `{ "status": "..." }` | `200` + object ที่แก้แล้ว | `400` สถานะผิด · `404` ไม่พบ |
| `DELETE` | `/api/requests/:id` | ลบคำร้อง | — | `204` ไม่มี body | `404` ไม่พบ |

## รูปแบบ Error

ทุก error ตอบเป็น JSON ที่มี field `error` เสมอ

```json
{ "error": "ข้อความที่ผู้ใช้ทั่วไปอ่านเข้าใจ" }
```

กรณี validation จะมี `details` เพิ่มมาเป็น array บอกว่าผิดตรงไหนบ้าง

| Status | เมื่อไหร่ | ฝั่งไหนผิด |
|---|---|---|
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง | ผู้ใช้ |
| `404` | ไม่พบทรัพยากรที่ขอ | ผู้ใช้ |
| `500` | โค้ดเซิร์ฟเวอร์ผิดพลาด | เซิร์ฟเวอร์ |

> **ตอน production จะไม่ส่ง stack trace กลับไป** — เปิดเผยโครงสร้างภายในให้คนภายนอกเห็นไม่ได้

## CORS

API อนุญาตให้เรียกจาก origin ที่กำหนดใน `CORS_ORIGIN` เท่านั้น

```
Access-Control-Allow-Origin: http://localhost:5173
```

**ถ้าเรียกจาก origin อื่น** เบราว์เซอร์จะบล็อกก่อนที่โค้ดจะได้เห็น response — จะเห็น error ใน Console ว่าถูกบล็อกโดย CORS policy

> ⚠ CORS เป็นกลไกของ **เบราว์เซอร์** เท่านั้น · Postman และ curl ไม่ถูกบล็อก เพราะไม่ใช่เบราว์เซอร์

## Data Model (เพิ่มใน Week 10)

API เก็บข้อมูลในฐานข้อมูล SQLite (`api/data/campus.db`) แยกเป็น 2 ตาราง

### ตาราง `users`

| คอลัมน์ | ชนิด | ข้อกำหนด |
|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT |
| `name` | TEXT | NOT NULL |
| `department` | TEXT | NOT NULL |
| `email` | TEXT | NOT NULL UNIQUE |

### ตาราง `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด |
|---|---|---|
| `id` | TEXT | PRIMARY KEY (รูปแบบ `REQ-NNN`) |
| `requester_id` | INTEGER | NOT NULL · FOREIGN KEY → `users(id)` |
| `request_type` | TEXT | NOT NULL · CHECK 4 ค่า |
| `location` · `details` | TEXT | NOT NULL |
| `priority` | TEXT | DEFAULT `'normal'` · CHECK |
| `status` | TEXT | DEFAULT `'pending'` · CHECK |
| `created_at` | TEXT | DEFAULT เวลาปัจจุบัน |

### ข้อสังเกตสำคัญ

**โครงสร้างในฐานข้อมูลไม่เหมือนรูปแบบที่ API ส่งออก**

- ฐานข้อมูลเก็บ `requester_id` (ตัวเลข) เพื่อไม่ให้ข้อมูลผู้ใช้ซ้ำ
- API คืน `requesterName` (ชื่อ) เพราะ frontend ต้องการแบบนั้น
- **ชั้น service เป็นตัวแปลงระหว่างสองรูปแบบด้วย `JOIN` และ `AS`**

ตอน POST — frontend ส่ง `requesterName` มา · service หา `id` ของชื่อนั้น ถ้ายังไม่มีก็สร้าง user ใหม่ให้ แล้วเก็บ `requester_id` ลงตาราง `requests`

# ทางเลือกฐานข้อมูล — SQLite, NoSQL และ async

> บันทึกตอบคำถามจากบท "อ่านเพิ่มเติม" (CP41)

## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB

ข้อมูลของเรา (users, requests) **มีโครงสร้างชัดเจนและมีความสัมพันธ์กัน** — คำร้องแต่ละใบชี้ไปหาผู้ใช้หนึ่งคนด้วย foreign key

SQL เหมาะกับข้อมูลแบบนี้เพราะ:
- บังคับโครงสร้าง (schema) และความถูกต้อง (constraint) ได้
- JOIN ดึงข้อมูลข้ามตารางได้ในคำสั่งเดียว
- ความสัมพันธ์ระหว่างตารางเป็นเรื่องหลักของ SQL

MongoDB (NoSQL) เหมาะกว่าเมื่อข้อมูล**ไม่มีโครงตายตัว** หรือแต่ละรายการหน้าตาต่างกันมาก เช่น log, เอกสารที่ field ไม่เท่ากัน

## 2. ถ้าวันหนึ่งต้องเปลี่ยนไป MongoDB จะกระทบชั้นไหน

| ชั้น | กระทบไหม | เพราะอะไร |
|---|---|---|
| Frontend | ❌ ไม่ | ยังเรียก API เดิม รับ JSON เดิม |
| Controller | ⚠ กระทบ | ต้องเติม `await` ทุกที่ (MongoDB เป็น async) |
| Service | ✅ กระทบเต็ม | เขียนใหม่ทั้งไฟล์ให้ใช้ MongoDB driver |
| Database | ✅ เปลี่ยน | จาก SQLite เป็น MongoDB |

> **ต่างจาก 4 ครั้งก่อน** ที่แก้แค่ service เพราะครั้งนี้เปลี่ยน sync→async ซึ่งเป็นการเปลี่ยน "สัญญา" ของ service จึงกระทบ controller ด้วย

## 3. async จำเป็นเมื่อไร ไม่จำเป็นเมื่อไร

| | ต้องรอไหม | ใช้ async ไหม |
|---|---|---|
| SQLite (ไฟล์ในเครื่อง) | อ่านเสร็จทันที | ❌ ไม่ต้อง |
| MongoDB Atlas (คนละเครื่อง) | รอข้อมูลข้ามเครือข่าย | ✅ ต้อง |
| เรียก API ภายนอก | รอเครือข่าย | ✅ ต้อง |
| อ่านไฟล์ขนาดใหญ่ | รอดิสก์ | ✅ ควร |

**หลักการ** — ใช้ async เมื่อต้อง**รอ**บางอย่างที่ไม่เสร็จทันที (เครือข่าย ดิสก์) เพื่อไม่ให้โปรแกรมค้างรอ

## 4. ไปเรียนต่อที่ไหน

- **วิชาฐานข้อมูลเทอมหน้า** — normalization, transaction, index เชิงลึก
- MongoDB University (ฟรี) · เอกสาร Mongoose
- หัวข้อ async/await ใน JavaScript เชิงลึก

# บันทึกการ Debug — Week 12

## BUG #0 · รายละเอียด 10 ตัวอักษรพอดีถูกปฏิเสธ

- **อาการ:** รายละเอียด 10 ตัวอักษรพอดีถูกปฏิเสธ ทั้งที่กำหนดขั้นต่ำ 10 ตัวอักษร
- **วิธีทำซ้ำ:** รัน unit test ด้วย `details: '1234567890'`
- **เครื่องมือ:** Vitest และ Boundary Value Testing
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/validators/requestValidator.js` ใช้เงื่อนไข `length <= MIN_DETAILS` ทำให้ค่า 10 ถูกปฏิเสธ
- **วิธีแก้:** เปลี่ยน `<= MIN_DETAILS` เป็น `< MIN_DETAILS`
- **test ที่กัน:** unit test `10 ตัวอักษร → ผ่าน (ตรงขอบพอดี)`

## BUG #1 · ลบคำร้องแล้วเพิ่มใหม่ได้ 500

- **อาการ:** เมื่อลบคำร้องตรงกลางแล้วสร้างคำร้องใหม่ ระบบตอบ 500
- **วิธีทำซ้ำ:** ลบ `REQ-002` แล้ว POST คำร้องใหม่
- **เครื่องมือ:** Log และ breakpoint ที่ฟังก์ชัน `nextId()`
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/services/requestService.js` ใช้ `COUNT(*) + 1` สร้าง ID ทำให้หลังลบรายการกลางสามารถสร้าง ID ที่มีอยู่แล้ว
- **วิธีแก้:** หารหัส `REQ-xxx` ล่าสุด แล้วนำเลขท้ายมาบวก 1
- **test ที่กัน:** integration test ลบรายการกลางแล้วเพิ่มใหม่ต้องตอบ 201 และ ID ไม่ซ้ำ

## BUG #2 · Dashboard นับกำลังดำเนินการเป็น 0

- **อาการ:** Dashboard แสดงกำลังดำเนินการ 0 ทั้งที่มีคำร้องสถานะ `in-progress`
- **วิธีทำซ้ำ:** ตรวจ GET `/api/requests` แล้วเทียบค่ากับ Dashboard
- **เครื่องมือ:** Browser DevTools Network และ frontend unit test
- **สาเหตุ (ไฟล์:บรรทัด):** `frontend/src/utils/requestSummary.js` ใช้ `in progress` แต่ API ส่ง `in-progress`
- **วิธีแก้:** เปลี่ยนค่าที่ใช้ในการนับเป็น `in-progress`
- **test ที่กัน:** `frontend/src/utils/requestSummary.test.js` → test นับสถานะ `in-progress` ได้ถูกต้อง

## BUG #3 · PUT คำร้องที่ไม่มีอยู่ได้ 500

- **อาการ:** `PUT /api/requests/REQ-999` ตอบ 500 แทน 404
- **วิธีทำซ้ำ:** PUT `/api/requests/REQ-999` พร้อม `{"status":"completed"}`
- **เครื่องมือ:** Stack trace และ integration test
- **สาเหตุ (ไฟล์:บรรทัด):** `api/src/controllers/requestController.js` เรียก `updated.id` ก่อนตรวจว่า `updated` เป็น null
- **วิธีแก้:** ตรวจ `if (!updated)` และตอบ 404 ก่อน แล้วจึงเรียก `console.log`
- **test ที่กัน:** integration test `คำร้องที่ไม่มีอยู่ → 404 (ไม่ใช่ 500)`

# รายงานปัญหาจากผู้ใช้ (Bug Reports)

ระบบนี้เปิดให้ทดลองใช้แล้ว ผู้ใช้แจ้งปัญหาเข้ามา 3 เรื่อง — **มีแต่อาการ ยังไม่มีใครรู้สาเหตุ**

## BUG #1 · ลบคำร้องแล้วเพิ่มใหม่ ขึ้น error

**ผู้แจ้ง:** เจ้าหน้าที่ฝ่ายอาคาร

> "วันนี้ลบคำร้องที่ซ้ำไป 1 รายการ แล้วพอนักศึกษาส่งคำร้องใหม่ ระบบขึ้นว่า 'เกิดข้อผิดพลาดภายในเซิร์ฟเวอร์'
> เมื่อวานยังส่งได้ปกติ"

- เกิดทุกครั้งหรือไม่: ไม่ทุกครั้ง — เมื่อวานส่งได้ วันนี้ส่งไม่ได้
- หน้าจอที่เกิด: หน้า "สร้างคำร้องใหม่"

## BUG #2 · ตัวเลข "กำลังดำเนินการ" บน Dashboard เป็น 0 ตลอด

**ผู้แจ้ง:** หัวหน้าฝ่ายบริการ

> "การ์ดสรุปด้านบนบอกว่ากำลังดำเนินการ 0 รายการ แต่ในรายการด้านล่างเห็นคำร้องสถานะ in-progress อยู่
> ตัวเลขอื่นดูถูกต้อง"

- เกิดทุกครั้งหรือไม่: ทุกครั้ง
- หน้าจอที่เกิด: Dashboard

## BUG #3 · เปลี่ยนสถานะคำร้องที่เพิ่งถูกลบ ขึ้น error 500

**ผู้แจ้ง:** เจ้าหน้าที่ฝ่าย IT

> "เพื่อนร่วมงานลบคำร้องไปแล้ว แต่หน้าจอของผมยังค้างอยู่ พอผมกดเปลี่ยนสถานะ ได้ error 500
> น่าจะต้องบอกว่า 'ไม่พบคำร้อง' มากกว่า"

- เกิดทุกครั้งหรือไม่: ทุกครั้งที่เปลี่ยนสถานะคำร้องที่ไม่มีอยู่
- ทดสอบซ้ำได้ด้วย: `PUT /api/requests/REQ-999` พร้อม `{ "status": "completed" }`
