# SECURITY_TEST.md — SQL Injection Test

## การทดสอบ SQL Injection

ทดสอบการส่งค่าที่มีคำสั่ง SQL ผ่าน `status` เพื่อดูว่าระบบสามารถป้องกัน SQL Injection ได้หรือไม่

### 1. ทดสอบเงื่อนไขที่เป็นจริงเสมอ

คำสั่งที่ใช้

```bash
curl "http://localhost:3001/api/requests?status=x'%20OR%20'1'='1"
```

ผลที่ได้

```text
[]
```

ระบบไม่คืนข้อมูลออกมาทั้งหมด แสดงว่าค่าที่ส่งเข้าไปถูกมองเป็นข้อความของ `status` และไม่ได้ถูกนำไปต่อเป็นคำสั่ง SQL

### 2. ทดสอบคำสั่ง DROP TABLE

คำสั่งที่ใช้

```bash
curl "http://localhost:3001/api/requests?status='%3B%20DROP%20TABLE%20requests%3B%20--"
```

ผลที่ได้

```text
[]
```

จากนั้นลองเรียกข้อมูลตามปกติอีกครั้ง

```bash
curl http://localhost:3001/api/requests
```

ยังสามารถดึงข้อมูลคำร้องได้ตามปกติ แสดงว่าตาราง `requests` ไม่ได้ถูกลบ

### 3. ทดสอบการต่อเงื่อนไขเพิ่ม

คำสั่งที่ใช้

```bash
curl "http://localhost:3001/api/requests?status=pending'%20OR%20status='completed"
```

ผลที่ได้

```text
[]
```

ระบบไม่ได้คืนรายการที่มีสถานะ `pending` หรือ `completed` ออกมา

## สรุป

จากการทดสอบทั้ง 3 แบบ ระบบสามารถป้องกัน SQL Injection ในส่วนของ `status` ได้ เพราะ query ใช้ parameterized query ด้วย `?` แทนการนำค่าจากผู้ใช้ไปต่อกับ SQL โดยตรง

# Campus Service — Full-Stack Integration

โปรเจกต์นี้เป็นระบบแจ้งคำร้องบริการภายในมหาวิทยาลัย พัฒนาด้วย React, Express และ SQLite โดย Week 11 นำงานจากสัปดาห์ก่อนมาประกอบเป็นระบบ full-stack ที่พร้อมรันในรูปแบบ production มากขึ้น ทั้งการแยก config ผ่าน environment variables, health check, logging และการเสิร์ฟ frontend กับ API ผ่านพอร์ตเดียว

## สถาปัตยกรรม 3 ชั้น

```text
React Frontend  --HTTP/JSON-->  Express API  --SQL-->  SQLite Database
 frontend/                      api/src/               api/data/
```

| ชั้น | หน้าที่ | ตำแหน่ง |
|---|---|---|
| Frontend | แสดงผล รับข้อมูลจากผู้ใช้ และเรียก API | `frontend/` |
| API | จัดการ route, validation, controller, service และ error | `api/src/` |
| Database | เก็บผู้ใช้และคำร้องอย่างถาวรในเครื่อง | `api/data/campus.db` |

การแยกเป็น 3 ชั้นช่วยให้แต่ละส่วนมีหน้าที่ชัดเจน ถ้าปรับหน้าเว็บไม่จำเป็นต้องแก้ SQL โดยตรง และถ้าเปลี่ยนวิธีเก็บข้อมูลก็สามารถจำกัดผลกระทบไว้ที่ชั้น service ได้มากที่สุด

## วิธีรันแบบ Development

ต้องใช้ Node.js 22.13 ขึ้นไป

Terminal 1:

```bash
cd api
npm install
npm run db:setup
npm run dev
```

Terminal 2:

```bash
cd frontend
npm install
npm run dev
```

จากนั้นเปิด `http://localhost:5173` และตรวจ API ได้ที่ `http://localhost:3001/api/health`

## วิธีรันแบบ Production

ที่โฟลเดอร์ `labs/week-11/source`:

```bash
npm install
npm run build
```

บน macOS/Linux:

```bash
NODE_ENV=production PORT=10000 npm start
```

บน Windows PowerShell:

```powershell
$env:NODE_ENV="production"
$env:PORT="10000"
npm start
```

เมื่อรัน production แล้ว หน้า React และ API จะอยู่ที่ origin เดียวกัน เช่น `http://localhost:10000/` และ `http://localhost:10000/api/health`

## Environment Variables

| ตัวแปร | ค่าเริ่มต้น | ใช้ทำอะไร |
|---|---|---|
| `NODE_ENV` | `development` | แยกพฤติกรรม dev/production |
| `PORT` | `3001` | พอร์ตของ Express |

## Health Check

`GET /api/health` ตรวจทั้งตัว API และการเชื่อมต่อฐานข้อมูล หากฐานข้อมูลพร้อมจะตอบ `200` พร้อม `status: "ok"` แต่ถ้าฐานข้อมูลใช้งานไม่ได้จะตอบ `503` เพื่อไม่ให้ระบบภายนอกเข้าใจผิดว่า service พร้อมใช้งาน

## การตัดสินใจออกแบบ

เลือก SQLite เพราะข้อมูลของระบบมีโครงสร้างชัด มีความสัมพันธ์ระหว่าง `users` กับ `requests` และขนาดงานยังไม่จำเป็นต้องมี database server แยกเครื่อง SQLite จึงติดตั้งง่ายและเหมาะกับการเรียนเรื่อง SQL และ full-stack integration

ใน production frontend ถูก build เป็น static files แล้วให้ Express เสิร์ฟไฟล์เหล่านั้น ทำให้ผู้ใช้เปิดเว็บและเรียก API ผ่านพอร์ตเดียวกัน ส่วน development ยังแยก Vite กับ Express เพื่อให้แก้ frontend แล้วเห็นผลได้เร็ว

# API Contract — Campus Service Request API

**เวอร์ชัน:** 2.0.0 · **Base URL:** `http://localhost:3001`
**รูปแบบข้อมูล:** JSON (`Content-Type: application/json`)

> **API Contract คืออะไร** — ข้อตกลงระหว่างคนทำ front-end กับคนทำ back-end
> ว่าจะคุยกันด้วย endpoint อะไร ส่งอะไรไป ได้อะไรกลับ
> มีไว้เพื่อให้สองฝั่ง**ทำงานคู่ขนานกันได้** โดยไม่ต้องรอกัน

---

## โครงสร้างข้อมูล Request

| field | ชนิด | คำอธิบาย | ตัวอย่าง |
|---|---|---|---|
| `id` | string | รหัสคำร้อง · ขึ้นต้นด้วย `REQ-` · เซิร์ฟเวอร์สร้างให้ | `"REQ-001"` |
| `requesterName` | string | ชื่อผู้แจ้ง · อย่างน้อย 2 ตัวอักษร | `"สมชาย ใจดี"` |
| `requestType` | string | ประเภท · 1 ใน 4 ค่าที่กำหนด | `"แจ้งซ่อม"` |
| `location` | string | สถานที่ · ห้ามว่าง | `"ห้องปฏิบัติการ 301"` |
| `details` | string | รายละเอียด · อย่างน้อย 10 ตัวอักษร | `"เครื่องปรับอากาศไม่ทำงาน"` |
| `priority` | string | `"normal"` หรือ `"urgent"` | `"urgent"` |
| `status` | string | `"pending"` · `"in-progress"` · `"completed"` | `"pending"` |

**ค่าที่ยอมรับของ `requestType`** — `แจ้งซ่อม` · `บริการบัญชีผู้ใช้` · `ขอใช้อุปกรณ์` · `อื่น ๆ`

## Endpoints

| Method | Endpoint | คำอธิบาย | Request body | สำเร็จ | ผิดพลาด |
|---|---|---|---|---|---|
| `GET` | `/api/requests` | ดูคำร้องทั้งหมด | — | `200` + array | — |
| `GET` | `/api/requests?status=` | กรองตามสถานะ | — | `200` + array | — |
| `GET` | `/api/requests/:id` | ดูคำร้องใบเดียว | — | `200` + object | `404` ไม่พบ |
| `POST` | `/api/requests` | สร้างคำร้องใหม่ | Request (ไม่ต้องมี `id`, `status`) | `201` + object ที่สร้าง | `400` ข้อมูลไม่ถูกต้อง |
| `PUT` | `/api/requests/:id` | เปลี่ยนสถานะ | `{ "status": "..." }` | `200` + object ที่แก้แล้ว | `400` สถานะผิด · `404` ไม่พบ |
| `DELETE` | `/api/requests/:id` | ลบคำร้อง | — | `204` ไม่มี body | `404` ไม่พบ |

## รูปแบบ Error

ทุก error ตอบเป็น JSON ที่มี field `error` เสมอ

```json
{ "error": "ข้อความที่ผู้ใช้ทั่วไปอ่านเข้าใจ" }
```

กรณี validation จะมี `details` เพิ่มมาเป็น array บอกว่าผิดตรงไหนบ้าง

| Status | เมื่อไหร่ | ฝั่งไหนผิด |
|---|---|---|
| `400` | ข้อมูลที่ส่งมาไม่ถูกต้อง | ผู้ใช้ |
| `404` | ไม่พบทรัพยากรที่ขอ | ผู้ใช้ |
| `500` | โค้ดเซิร์ฟเวอร์ผิดพลาด | เซิร์ฟเวอร์ |

> **ตอน production จะไม่ส่ง stack trace กลับไป** — เปิดเผยโครงสร้างภายในให้คนภายนอกเห็นไม่ได้

## CORS

API อนุญาตให้เรียกจาก origin ที่กำหนดใน `CORS_ORIGIN` เท่านั้น

```
Access-Control-Allow-Origin: http://localhost:5173
```

**ถ้าเรียกจาก origin อื่น** เบราว์เซอร์จะบล็อกก่อนที่โค้ดจะได้เห็น response — จะเห็น error ใน Console ว่าถูกบล็อกโดย CORS policy

> ⚠ CORS เป็นกลไกของ **เบราว์เซอร์** เท่านั้น · Postman และ curl ไม่ถูกบล็อก เพราะไม่ใช่เบราว์เซอร์

## Data Model / ฐานข้อมูล

ใน Week 10 ระบบเปลี่ยนจากการเก็บข้อมูลในไฟล์ JSON มาใช้ฐานข้อมูล SQLite โดยมีตารางหลัก 2 ตาราง คือ `users` และ `requests`

### ตาราง users

| คอลัมน์ | รายละเอียด |
|---|---|
| `id` | รหัสผู้ใช้ เป็น Primary Key |
| `name` | ชื่อผู้ใช้ |
| `department` | สาขาหรือหน่วยงาน |
| `email` | อีเมล และห้ามซ้ำกัน |

### ตาราง requests

| คอลัมน์ | รายละเอียด |
|---|---|
| `id` | รหัสคำร้อง เช่น REQ-001 |
| `requester_id` | รหัสผู้แจ้ง เชื่อมกับ `users.id` |
| `request_type` | ประเภทของคำร้อง |
| `location` | สถานที่ |
| `details` | รายละเอียด |
| `priority` | ระดับความสำคัญ |
| `status` | สถานะของคำร้อง |
| `created_at` | วันที่และเวลาที่สร้าง |

ความสัมพันธ์ของตารางคือ user 1 คนสามารถมีคำร้องได้หลายรายการ โดย `requests.requester_id` เป็น Foreign Key ที่อ้างถึง `users.id`

## รูปแบบข้อมูลในฐานข้อมูลกับ API

ข้อมูลที่เก็บในฐานข้อมูลกับข้อมูลที่ส่งให้ frontend มีรูปแบบไม่เหมือนกันทั้งหมด

ในฐานข้อมูลจะเก็บ `requester_id` เพราะไม่ต้องการเก็บชื่อผู้แจ้งซ้ำในทุกคำร้อง แต่ API จะส่ง `requesterName` ให้ frontend เพื่อให้ใช้งานได้เหมือนเดิม

ใน `requestService.js` จึงใช้ `JOIN` เชื่อมตาราง `requests` กับ `users` และใช้ `AS` เปลี่ยนชื่อคอลัมน์ เช่น `request_type` เป็น `requestType`

## พฤติกรรมของ POST

เวลาสร้างคำร้องใหม่ frontend จะส่ง `requesterName` มา แต่ฐานข้อมูลต้องเก็บเป็น `requester_id`

service จะค้นหาชื่อผู้ใช้ก่อน ถ้ามีผู้ใช้นี้อยู่แล้วก็ใช้ id เดิม แต่ถ้ายังไม่มี จะสร้าง user ใหม่แล้วนำ id ที่ได้มาเก็บในคำร้อง

ทำให้ frontend ไม่ต้องเปลี่ยนรูปแบบข้อมูลจาก Week 07 และฐานข้อมูลก็ยังเก็บข้อมูลแบบไม่ซ้ำกัน

# Database Choices — Week 11

## 1. ทำไมโปรเจกต์นี้เลือก SQLite แทน MongoDB

โปรเจกต์นี้มีข้อมูลที่โครงสร้างค่อนข้างชัด เช่น ผู้ใช้และคำร้อง และสองส่วนนี้มีความสัมพันธ์กันผ่าน `requester_id` จึงเหมาะกับฐานข้อมูลเชิงสัมพันธ์อย่าง SQLite มากกว่า ในงานขนาดนี้เรายังไม่จำเป็นต้องเปิด database server แยกอีกตัว ทำให้ SQLite ตั้งค่าและทดสอบง่ายกว่า MongoDB ด้วย อีกเหตุผลคือเราใช้ SQL, foreign key และ constraint เพื่อตรวจความถูกต้องของข้อมูลได้ตรงกับสิ่งที่ระบบต้องการ

## 2. ถ้าวันหนึ่งต้องเปลี่ยนไป MongoDB จะกระทบชั้นไหนบ้าง

ส่วนที่กระทบหลักคือ **service** เพราะ query แบบ SQL จะต้องเปลี่ยนเป็นการเรียก MongoDB และวิธีแปลงข้อมูลก็จะเปลี่ยนตามไปด้วย แต่ MongoDB ที่ต่อผ่าน network ทำงานแบบ async ดังนั้น **controller ก็จะได้รับผลกระทบด้วย** เพราะต้อง `await` ผลจาก service ก่อนส่ง response กลับ ส่วน route และ frontend ควรเปลี่ยนน้อยหรือไม่ต้องเปลี่ยน ถ้าเรายังรักษา API contract เดิมไว้ นี่ต่างจากตอนเปลี่ยน JSON เป็น SQLite ที่ service ยังตอบแบบ synchronous ได้

## 3. async จำเป็นเมื่อไร และไม่จำเป็นเมื่อไร

async จำเป็นเมื่อโปรแกรมต้องรอ I/O ที่ใช้เวลาและไม่ควรบล็อกงานอื่น เช่น เรียก API ผ่าน network หรือคุยกับฐานข้อมูลที่อยู่คนละเครื่องอย่าง MongoDB server ระหว่างรอ Node สามารถไปทำ request อื่นต่อได้ ส่วน SQLite แบบ `node:sqlite` ในงานนี้เปิดไฟล์ฐานข้อมูลในเครื่องและใช้ API แบบ synchronous จึงไม่จำเป็นต้องทำทุกฟังก์ชันเป็น async การใส่ async โดยไม่มีเหตุผลไม่ได้ทำให้ระบบเร็วขึ้น และยังทำให้โค้ดซับซ้อนขึ้นโดยไม่จำเป็น
